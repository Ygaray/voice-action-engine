## Execution notes

- Open questions from the research, resolved here (record each in the SUMMARY):
  - **Q2, single-entry undo:** `undoEntry` is offered for isolated entries only. An entangled entry gets
    `Refused(ENTANGLED)` with no expansion to its component. `undoAll` covers entangled actions.
  - **Q4, JournalStore shape (D-06 locks "in-memory + optional store interface"):** a write-through mirror with two
    methods, `save(UndoGroup)` and `delete(groupKey)`. It carries no snapshots and no fingerprints, and there is no
    `loadAll`. The journal therefore still "does not survive process death" exactly as D-06 documents it. Loading can be
    added additively later as an interface method with a default body. This is the smallest frozen surface that honors
    D-06 (research assumption A7).
  - **Q6, N and no-op entries:** an applied entry that called `nothingWritten()`, or that declared nothing, counts in
    N (D-02 counts applied actions) and appears in `Complete.restored`, because there is nothing to write.
- Defaults: `maxGroups = 50`, `maxAgeMillis = 3_600_000` (one hour since the group's last activity). The age bound
  keeps user-data snapshots from lingering (ASVS V8). Both are constants in UndoJournal.kt, never magic numbers.
- Stdlib only. Never call the store, an adapter or a compensator under the lock. Store calls go through guardedCall:
  a fault increments `storeFaults`, and cancellation propagates.
- No planning ids in source comments or KDoc.
