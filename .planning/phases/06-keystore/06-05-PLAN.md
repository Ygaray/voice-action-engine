<objective>
Plug `:keystore` into the provider seam (KEY-04): `KeystoreCredentialSource` implements the existing `CredentialSource` and collapses the four `KeyState`s onto the existing `CredentialLookup` leaves (Runtime Decision credential-adapter, D-09), so a restored-backup user is asked to re-enter the key instead of being told the provider is not configured. Prove it through the real `commandPipeline`, then sweep every sink for the key (canary) and every compiled class for the house public-shape rules.

Purpose: SC4's JVM half; the cloud call path gets its key from the app's encrypted store with every failure typed, and nothing secret leaks on the way.
Output: one public adapter and four test classes.

Contention: the phase runs strictly sequentially, one plan per wave (wave 5 is this plan only; it starts after 06-04 has merged), so no two plans ever run `:keystore` Gradle tasks at the same time; this plan reads `:core` but runs only `:keystore` tasks, never two Gradle invocations at once, until its final `:keystore:check :core:check`.
</objective>
